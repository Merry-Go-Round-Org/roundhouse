F1 Split Policy

How the platform keeps train, validation and test memberships reproducible while protecting existing legacy models.

Available now: upload a source dataset and dataset.json, optionally with a split CSV. When the split is omitted for an existing UCI/ULB dataset, the backend has a canonical reuse path.

Not enabled yet: automatic generation for arbitrary new datasets, server-issued new dataset IDs, and authenticated split downloads. These are proposed F1 contract rules, not current uploader guarantees.

What to upload

  1. Source dataset: original .csv, .xls or .xlsx, with the expected target and columns.
  2. Dataset descriptor: dataset.json, including the source SHA-256 and dataset metadata. Current UCI/ULB descriptors also require the canonical split hash and partition counts.
  3. Split File (Optional): .csv with headers row_id,split (or row_id,partition) and exactly one assignment per source row. Leave blank for canonical reuse of an existing UCI/ULB dataset.

The split file is not a second dataset and must not be regenerated just because the file picker is empty.

Target F1 safeguard: compare the original source hash and split hash against a trusted server registry, not just hashes supplied by the uploader. Reject mismatched explicit splits; never silently replace these memberships.

UCI IDs come from the original ID column. ULB IDs follow original zero-based CSV row order, so rearranging ULB source rows is not equivalent.

New datasets

Proposed deterministic generation rule (not implemented in ingestion yet):

  1. Require a unique, stable, non-empty row_id per record and a binary target with both classes. Do not use uploaded row position as a generic ID.
  2. For independent classification data only, allocate approximately 60% train / 20% validation / 20% test within each class, with a fixed documented seed and versioned algorithm.
  3. Rank each row using SHA-256 of a stable seed, algorithm version and row ID; use the row ID to break ties. Serialize the generated CSV in sorted row-ID order so identical inputs and configuration produce identical bytes.
  4. Require at least five examples of each class so all three partitions can contain both classes. Reject insufficient or malformed input.
  5. Time-dependent, grouped, survival and other specialized datasets need an explicit appropriate policy or uploaded split. Do not silently use stratified random splitting.

Identity proposal: the backend issues a new dataset family ID in the form ds_<32-hex UUID> and a separate immutable version_id. Existing uci_credit and ulb_fraud IDs never change. Repeated uploads must be idempotent or return a clear conflict rather than rewriting a registered version.

Validation and model safety

  • Reject missing, duplicated, unknown or overlapping row IDs, invalid partitions, source/split hash mismatches and incorrect counts.
  • Keep the test partition unavailable to model-development agents; validate leakage boundaries and target/audit-column restrictions.
  • Bind every model to the exact immutable dataset version and split hash. A model trained with the frozen UCI/ULB split is not compatible with a newly generated split on the same source.
  • The server response should publish source and split hashes, partition counts, origin (uploaded, canonical_reused or auto_generated), algorithm/seed when generated, and an immutable version ID.
  • Future downloads must be authenticated, scoped to the saved dataset version and byte-verified against the recorded split hash.

Current backend validations cover many malformed assignments; trusted hash pinning, strict model-to-split binding and new-dataset creation remain outstanding F1 acceptance work.
